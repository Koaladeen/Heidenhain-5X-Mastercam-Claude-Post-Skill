1Introduction

The skill gives Claude a working method and a collection of known problems for developing Mastercam MP post processors (.pst) for Heidenhain controls. It covers new posts, changes to existing posts, posting errors, and the replacement of vendor posts whose source is not available, by comparing NC output.

The content was written from experience on production machines: 5-axis machining centres with A/C and B/C tables and 3-axis machines generated from the same master post. It describes procedures and observed behaviour. It does not reproduce Mastercam or Heidenhain documentation and contains no vendor post code.

2Installation

Copy the skill directory into a Claude Code skills directory. Claude loads the skill when a task concerns Mastercam posts for Heidenhain machines.

# available in all projects of the user
cp -r skills/mastercam-heidenhain-posts ~/.claude/skills/

# available in one project only
cp -r skills/mastercam-heidenhain-posts <project>/.claude/skills/

The scripts in scripts/ require Python 3 and no additional packages.

3Ground rules

The skill instructs Claude to follow these rules on every task.

  1. No direct edits of the live post. Changes are made on a local copy. Every replaced version is backed up. Deployment happens only on the user's instruction, after a hash comparison with the last deployed version.
  2. Posts are built, not edited by hand. A build script creates the post from a base post. Each change is a text replacement that checks how often its source text occurs.
  3. CRLF line endings are kept. Many editors and shell tools convert them silently.
  4. Encrypted posts are not decrypted. Their NC output may be used as the specification.
  5. Changes are verified with NC files. The same part is posted with the old and the new post and the differences are evaluated. New functions are checked in the control's test run graphics and with a dry run.
  6. Machine data is not assumed. Brake and coolant M functions, rotary axis travel, PLANE mode, probe tool number and free Q/QR parameters are requested from the user or made configurable.

5Known pitfalls

The following problems caused the largest delays in practice. Details are in references/mp-language.md.

Table 2 - MP and engine behaviour

Wrong branch executedA one-line else belongs to the line directly before it. Write branches as bracketed blocks.
Empty line missingA block without content is dropped. Output a string containing one space.

7Cycles and probing

The drill cycle list contains 8 standard and 12 custom entries. The engine variable drillcyc$ counts from zero: custom cycle 9 corresponds to drillcyc$ = 8. Existing operations store the list position, so a replacement post keeps the cycle order of the old post. Unused positions stop posting with a message.

Probing cycles (TCH PROBE 4xx) can be assigned to free custom cycles when no CAM probing option is available. The drill point is the nominal position, the depth is the measuring height, and the dialog labels name the Q parameters. For the probe tool the post writes no spindle start, no coolant and no breakage check.

41 TOOL CALL 30 Z S0
42 TCH PROBE 412 BZPKT KREIS INNEN ~
    Q321=+25 ;MITTE 1. ACHSE ~
    Q322=+40 ;MITTE 2. ACHSE ~
    Q262=+30 ;SOLL-DURCHMESSER ~
    ...
Note

Field labels can be redefined per cycle in the control definition. Verify which engine variable a field supplies by entering distinct test values and posting.

8Serial engraving

A free drill cycle engraves a prefix and a counter value at each drill point. The counter is a QR parameter, so its value is retained after power off. It is incremented after each number and can be raised to a start value. The prefix is output directly; the digits 0 to 9 are label subprograms after M30, scaled with CYCL DEF 26 and rotated with CYCL DEF 10. The font is supplied as assets/stroke_font.json (single-stroke, cell 0.6 x 1, characters A-Z, 0-9, - / .).

88 Q1701 = QR100
89 Q1710 = INT ( Q1701 / 1000 ) - 10 * INT ( Q1701 / 10000 )
90 CALL LBL 900
97 QR100 = QR100 + 1

9Replacing a post

When the source of the existing post is not available, its NC output serves as the specification. The same program is posted with both posts on the same day; nc_diff.py reduces the differences to patterns. Rules that are not visible directly are derived from the data and confirmed with a second program.

Table 4 - Typical difference patterns
PatternUsual cause
X+.2 / X+0.2Format flags
CC/C / LLinearisation of very small arcs
F after every FMAXFeed format reset in the post
Additional blocks between operationsNull tool changes within one operation
Missing FUNCTION RESET TCPMTool change call 1002 not sent
Different coolant M functionsOperations refer to entries of a previous coolant list

Example: in one case neither radius nor arc height explained which arcs the old post output as straight lines. The sweep angle did: all arcs below 0.1 degrees were written as L blocks.

10Scripts

Table 5 - Scripts in scripts/
ScriptFunction
patch_tool.pyText replacement with occurrence check, CRLF-safe file handling. With --check: line endings, duplicate definitions, undeclared identifiers.
nc_diff.pyCompares two programs without block numbers and date lines and groups the differences by pattern.
arc_rules.pyLists arcs output as straight lines by one post, with radius, chord, height and sweep angle.
safe_deploy.pyCopies a post to its live location only if the live file is unchanged since the last deployment; creates a backup and verifies the copy.
 
python scripts/nc_diff.py part-old.h part-new.h --show 10

python scripts/safe_deploy.py --live P:/posts/my_tnc.pst --new work/my_tnc.pst \
    --expect <md5-of-last-deploy> --backup-dir P:/posts/backup

12Safety and legal

Caution

Errors in a post processor can cause collisions, damage to the machine and the workpiece, and injury. Check every posted program in the test run graphics of the control and with a dry run, Z axis retracted, before machining. M functions, Q/QR parameters and travel limits shown in this document are examples; use the values from the documentation of your machine.
